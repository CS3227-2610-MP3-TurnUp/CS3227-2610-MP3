# Reflections on developing TurnUp

Looking back at TurnUp, the biggest change was in how I judged progress. At first, I put considerable effort into setting up the development process: organising specifications, defining agents and adapting my MP2 workflow. As development continued, I became more concerned with whether those arrangements were actually helping me build the right product. Four experiences, in particular, changed how I would approach another AI-assisted project.

## 1. More agents gave me more coordination work before they gave me more progress

Converting my MP2 orchestrator skill into a multi-agent orchestrator seemed like a sensible next step. I already had a workflow for planning, implementing and testing features, so assigning those stages to specialist agents appeared to make it more systematic. In practice, I found the conversion inefficient and wasteful of tokens for routine work. I had designed a team of agents before deciding which problems actually needed a team.

The account feature shows why. Signup/login planning involved an explorer and a requirements analyst, followed by an implementation worker and an independent verifier. Credentials/profile planning brought in another analyst and inventory investigation. However, the main agent still had to understand their findings, resolve inconsistencies, update the specifications and coordinate the next step. Delegation moved work between agents, but did not remove the need for someone to understand the complete feature. [1, entries 01–02; 2, entries 01–04]

I had confused a useful sequence of activities with a useful division of labour. Planning, coding and testing need to happen, but they often depend heavily on the same context. Passing that context between agents introduced another opportunity to repeat reading or lose an important qualification. For a small change, keeping the same agent working through the stages was often a more sensible starting point. I later moved routine work back into the main chat; the registration log records substantial implementation and verification without delegating those stages. [3, entries 06–10]

That does not mean every additional agent was wasted. During credentials/profile implementation, independent review identified password-eye controls positioned incorrectly outside their intended wrappers. That finding led to a concrete correction. Similarly, the initial Student AI work gave a specialist the evidence/state core while the main agent handled the interface. These assignments had a clearer purpose: find something the author missed, or own a genuinely separable part of the implementation. [2, entry 03 and linked verification; 4, entry 02]

My preferred approach is now to keep one agent responsible for the feature and justify each extra agent by the contribution I expect from it. I would test a specialist by whether it finds consequential defects or produces work that can be integrated, rather than by whether its role description sounds thorough. Its brief should name the requirement and permitted files; its handoff should identify the version it worked on, what it checked and what remains uncertain. A confident “done” is much less useful than knowing that offline tests passed but database checks could not run. A reviewer also needs to inspect the source and requirements: a fresh agent can repeat the author's mistake if it relies entirely on the author's summary.

There is a tradeoff here. When I later requested main-agent-only work, I also gave up a fresh independent perspective on those changes. Earlier independent review did not automatically cover later edits. Nor do my logs contain a fair, complete comparison from which I can calculate a percentage token saving. My conclusion is narrower: the automatic delegation I introduced created coordination that I did not consistently need. Next time, I would start with selective delegation and expand it only when its benefit becomes visible.

## 2. A specification was most useful when it exposed a decision I had not really made

One example was changing account credentials. The original implementation signed users out after both username and password changes. During browser verification, I clarified that changing a username should keep users signed in; only an actual password change should revoke their sessions. This required updates to the policy, implementation and tests, followed by SQL and browser rechecks. [2, entries 03–04]

Before that interaction, “allow users to edit their credentials” could have sounded sufficiently clear. It was not. The agent still needed an answer to a product question with consequences for both security and usability. Seeing the behavior made the missing distinction more obvious than reading the feature description had. One subsequent check covered changing a password immediately after renaming on the same page, because the client needed to use the updated credential revision. The requirement became useful when it described what should happen through that whole sequence.

Registration exposed the same issue on a larger scale. I moved from considering custom forms to a simple Attend action without entered details, then later requested a required event-specific Name and phone number or Telegram handle. The account profile remained optional; the registration captured separate contact details for that event. Those choices affected validation, privacy, storage and the interface. They could not be handled safely as small wording changes to the original plan. [3, entries 01–03 and 12]

When the contact rule changed, a SQL test still expected a null captured name and failed. Updating that assertion was appropriate because the intended behavior had explicitly changed. This helped me distinguish maintaining a test from weakening one merely to make it pass. The reason for the change needed to come from the requirement, not from the inconvenience of a failing check.

I now think a good specification should make the difficult distinctions clear before implementation: who may perform an action, what changes, what must remain unchanged and what happens when the request is stale or a dependency fails. It should also say which decisions are still open. I would ask whether another implementer could predict the important outcomes without having to invent rules on my behalf.

This also changed how I understood dependencies with Keith. Initially, I treated work-package order as a reason to wait for an entire earlier package. The later registration plan instead separated ready components from the parts that needed a shared schema or publication handoff. Student AI components could likewise be developed with synthetic content before connecting real published events. [3, entry 07; 4, entries 01–02 and 19–22]

The practical value of SDD was therefore not a fixed document written once at the start. It was having a shared place to make assumptions explicit and revise them consistently. That allowed some work to proceed in parallel while keeping genuinely shared decisions visible.

## 3. Passing tests sometimes meant I had asked the wrong question

Signup/login initially passed 163 offline tests. Later, a real SQL test with 35 concurrent attempts produced 28 admissions and seven Prisma transaction failures, rather than the expected rate-limit denials. A bounded-wave version subsequently passed six SQL tests, but the original burst-availability limitation remained in the record. [1, entries 02 and 05]

This was an uncomfortable but useful distinction. A request failing is not necessarily evidence that a security limit worked. If it failed because the transaction could not complete, I had learned something about availability rather than demonstrated correct rate limiting. Changing the workload to bounded waves gave useful evidence about that workload; it did not solve the original burst failure. Reporting only the later green result would have hidden the more important discovery.

The AI feature gave me another version of this lesson. A saved live request returned HTTP 200 but reached its 512-token completion limit without producing a usable answer. It consumed 361 prompt tokens and 512 completion tokens. A later attempt with a larger output cap failed without an HTTP response. Increasing the limit was therefore not enough to establish that the feature worked. [4, entries 12–14]

Likewise, one Preview deployment completed successfully while chat was deliberately disabled on Vercel. Hosted chat required a later implementation with authenticated routes and durable usage controls. The deployment result was real, but it answered a different question from whether a Student could actually ask about an event online. [4, entries 24–26]

These experiences made test counts less persuasive to me on their own. I need to know what each test exercises and what kind of evidence it provides. A simulated provider response can test how my code handles that response, but cannot show that the real model will produce it. A database test can establish transaction behavior without establishing that the browser gives understandable feedback.

In another project, I would choose checks by starting with a possible failure in the user's experience: two people get the last seat, a failed answer consumes repeated requests, or a deployed feature remains inaccessible. I would then work backwards to the checks needed to challenge that failure. This is a better use of tests than accumulating assertions that repeat the implementation's own assumptions.

## 4. I could give AI more responsibility only by keeping its authority limited

TurnUp had several places where untrusted text could enter: proposal documents, public event descriptions, Student questions, form labels and even fixtures read by development agents. The risk was not identical in each case. A script-like account name could affect rendering; an instruction inside an event description could try to influence an answer; an instruction inside a development fixture could try to redirect an agent's tools.

The development records include escaping checks and bounded malicious-input fixtures with checks for unauthorised effects. However, escaping HTML does not prove that an LLM will ignore an instruction, and a few unsuccessful injection attempts do not establish that the system is immune. I found it more useful to think about what an influenced model would actually be allowed to do. [2, entry 05 and linked verification; 4, entries 02 and 17]

For Student answers, application code selected the current approved public source and rechecked the session, publication and evidence before returning the result. Private proposal material and replies were not fallback knowledge. This reduced reliance on the model obeying a sentence such as “do not reveal private information.” It also addressed a less obvious problem: a response could become unsafe after its event was withdrawn or replaced, even if the original question contained no malicious instruction. [4, entries 21–23]

Human approval needed the same separation between information and authority. An instruction found in a document, fixture or another agent's summary should not become permission to change scope or make a live request. Our process used explicit plan approval and separate decisions for live usage and deployment. Local experiments had code-enforced limits on attempts, output, request spacing and expiry; hosted usage needed durable database controls. A local testing allowance did not automatically authorise a hosted budget, and Preview and Production received separately approved pools. Using my own Student key also led to explicit key selection without falling back to Keith's Organiser key. [4, entries 10 and 25–27; 5, entry 01]

These boundaries were useful, but the answer itself still needed scrutiny. My pipeline checked that quoted evidence existed in the approved source. That did not prove that the model's surrounding explanation followed from the quote. A genuine quotation can still accompany an unsupported conclusion. Later conversational refinements recorded this limitation, while ordinary casual questions also exposed how strict response formatting could produce an unhelpful technical error. [4, entry 17; 6, entries 01–03]

I therefore would not judge the AI feature solely by whether it rejected attacks or returned valid JSON. It also needs to handle missing facts, ambiguous questions and genuine service failures honestly. A technical failure should not blame the user for asking a valid question, and suggesting contact with an Organiser should not imply that a message has already been sent.

Across these experiences, my role shifted from arranging more AI activity to deciding what authority to grant and what evidence to trust. The development process became more useful when it helped me make those decisions, rather than becoming another elaborate system to maintain.
