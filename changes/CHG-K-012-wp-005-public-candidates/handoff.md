## Producer and consumer contract

POST `/api/organiser/events/[id]/public-candidates` accepts exactly `{expectedVersion, expectedPreparationRevision}`. Both are nonnegative integer revisions; null preparation uses revision0. No caller-supplied source fields are accepted. Owner/session, editable event, complete saved public fields, resolved required clarifications and expected revisions are checked against authoritative storage. The saved snapshot is read again after inference; changed ownership/session/state/revisions/source prevents delivery. Generation does not write Event fields, preparation, preview approval or publication. Explicit Apply changes Other only; no duplicate description suggestion is generated. Blank candidates cannot clear Other, and all-unanswered output is explained with optional organiser answer/add controls.

Success returns `{ok:true,eventVersion,preparationRevision,candidates}`. Candidates contain `{answeredFaqs:[{question,answer,references}],unansweredQuestions,renderedOther}`. References contain `{field,quote}` and must match allowlisted saved public fields exactly. Date references use readable Singapore time. The model supplies FAQ questions and references; the server derives answers from validated exact quotes. Unsupported questions remain optional organiser prompts. Questions must form a nonempty list of at most six entries; relevance/completeness still need later model evaluation.

Only intended-public title, description, start/end, location, capacity, fee, openTo, preparation and Other enter the prompt. Event private `preparation` metadata is a different structure from the public `fields.preparation` attendance-condition text; it is excluded together with PDF/fulltext, private issue evidence/attribution and participant data. Candidates and organiser answers remain browser-local until explicit application and normal save. No new Student reader or registration/thread dependency is introduced.

## Integration paths and limits

Shared contract/renderer: `src/features/proposal-assistance/public-candidates.ts`. New prompt/processor: `src/server/proposal-assistance/public-candidates/`. Read-only saved readiness helper: `src/server/events/service.ts`. UI: `src/components/events/public-content-assistance.tsx`, integrated into the existing EventEditor. Existing extraction prompt v6 is unchanged; public FAQ candidates have their own v3 prompt, with a nonempty FAQ-only schema and explicit participant topics/examples; finite server-only rejection codes identify validation failures without exposing raw model/event content. Dated verification snapshots distinguish the earlier v1/v2 live synthetic checks from current v3 deterministic-only verification.

The action shares existing local synthetic transport, owner admission and durable provider budget. It does not increase allowance, retry automatically, enable hosted inference or alter the profile. K-011 migration/client regeneration remains a prerequisite on other databases. Production retention/cleanup, hosted provider activation and comprehensive labelled model evaluation remain deferred. This handoff does not claim complete WP-005 acceptance.

Follow the [local walkthrough](../../docs/wp-005-proposal-integration.md#public-content-candidates-walkthrough--local-synthetic-only). Tests use controlled doubles unless verification explicitly states otherwise. No new live provider/DB/gate operation or deployment is implied.
