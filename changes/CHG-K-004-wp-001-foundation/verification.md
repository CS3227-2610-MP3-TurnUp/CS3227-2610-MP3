## 19 October 2026 migration safety correction

The three PR review reports were valid. `migrate reset` previously fell through to the `other` intent, allowing a production-labelled direct URL to reach Prisma; Prisma reset drops the database/schema and `--force` skips confirmation. Prisma 7.10.1's pinned PostgreSQL URL parser defaults `sslaccept` to `accept_invalid_certs` and supports only `sslmode=disable`, `prefer`, or `require`; unsupported `verify-full` falls back to `prefer`. The corrected config classifies reset explicitly and rejects it under production labels before reading `MIGRATION_DATABASE_URL`. Direct migration and shadow URLs now require the supported `sslmode=require&sslaccept=strict` pair; pooled runtime URL validation remains separate.

The Foundation Engineer changed `src/server/config/environment.ts`, `prisma.config.ts`, `tests/foundation/environment.test.ts`, `README.md`, and `.env.example` on branch `4-foundation-stack` at parent `7d4d1b983c4104f758c476fc345c7de20efb1f58`. The author's frozen install could not reach registry DNS, and offline installation lacked `jsesc@3.1.0`. Using the complete pinned dependency tree from the hosted worktree through a temporary symlink, the verifier reproduced 13/13 default Vitest tests, TypeScript `tsc --noEmit --incremental false`, ESLint, and `git diff --check`; the original foundation `node_modules` cache was restored. Synthetic configuration checks rejected production reset before URL validation, allowed non-production reset without a shadow URL, rejected invalid TLS/duplicate/override parameters on both direct URLs, and preserved runtime `pg` certificate validation. Prisma's actual `loadConfigFromFile` rejected production reset and loaded non-production reset and production deploy with synthetic URLs. No Prisma reset or live database operation was run.

Production build, live Neon migration/replay and hosted checks remain unrun for this correction.
