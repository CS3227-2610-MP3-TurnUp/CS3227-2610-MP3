Illustrative future CLI sequences, after authenticated project configuration and required checks (not executed here):

```bash
# Preview environment
vercel pull --yes --environment=preview --token="$VERCEL_TOKEN"
vercel build --token="$VERCEL_TOKEN"
vercel deploy --prebuilt --token="$VERCEL_TOKEN"

# Production environment, in its separate trusted release job
vercel pull --yes --environment=production --token="$VERCEL_TOKEN"
vercel build --prod --token="$VERCEL_TOKEN"
# Required serialized migration/release checks precede upload.
vercel deploy --prebuilt --prod --skip-domain --token="$VERCEL_TOKEN"
# Capture its URL as VERCEL_DEPLOYMENT_URL; only after required candidate checks:
vercel promote "$VERCEL_DEPLOYMENT_URL" --token="$VERCEL_TOKEN"
```

[Pull](https://vercel.com/docs/cli/pull) downloads settings and environment values into `.vercel/`; [build](https://vercel.com/docs/cli/build) emits `.vercel/output`; [deploy --prebuilt](https://vercel.com/docs/cli/deploy) uploads that output. Pull/build/deploy must use the same project and target; production cannot reuse a preview-target build. The CLI documents a first-deployment production exception even without `--prod`, so bootstrap must not be mistaken for an isolated preview. `--skip-domain` defers automatic production aliasing; [promote](https://vercel.com/docs/cli/promote) assigns the checked production-target candidate later. Candidate code still runs before promotion and migrations affect the shared target database: use only compatible migrations and the assigned synthetic checks, with recovery ready. The implementation must account for documented prebuilt limitations, including build-time system variables, and validate required branch metadata rather than assuming native-Git behaviour.

Keep `.vercel/` environment caches and real local env files ignored and out of logs/general artifacts. Only the intended compiled deployment output is uploaded; verify that it does not contain accidental credential/private-data material. Environment pulls make secrets available to the trusted runner: never run them for untrusted PR code or upload the whole `.vercel/` directory as a diagnostic artifact. Builds must not query production private records. Production environment values are configured outside Git and remain unavailable to development agents inspecting private production data. Application server configuration, SoC authentication and deployment authentication remain separate boundaries.

Required future checks include: failed pre-upload checks prevent migration/upload, while failed candidate checks prevent promotion; missing/invalid deployment token or wrong project/target fails without fallback; preview and production receive their own configuration/data; no deployment secrets reach untrusted PRs or diagnostics; serialized migration failure prevents production upload; returned URL/revision/target matches the tested artifact; protected preview and hosted runtime checks succeed. These refine planned DEP02/DEP03, SEC06 and T15/T28 evidence, without adding product requirements or recording any test as passed.

### Database and migration operations

Mark credential-reading/database modules server-only and exclude their imports from client bundles under the [Next server/client boundary](https://nextjs.org/docs/app/getting-started/server-and-client-components). Use `DATABASE_URL` for the pooled runtime connection and a separate direct `MIGRATION_DATABASE_URL` for the migration runner, with least-required access. These are selected application configuration names, not a claim that Prisma automatically recognises the migration variable. Wire the CLI configuration explicitly and verify chosen driver/migration compatibility with Neon's connection modes. [Environment-variable handling](https://nextjs.org/docs/pages/guides/environment-variables) does not itself provide application authorisation.

Use `prisma migrate dev` only against disposable development data; review/version generated SQL. Validate and explicitly configure the [shadow database](https://www.prisma.io/docs/orm/v7/prisma-migrate/understanding-prisma-migrate/shadow-database) needed by the chosen development migration workflow on an isolated synthetic Neon resource; it must never target production or another developer's active database. Replay history on a fresh isolated test database and exercise an upgrade fixture before a serialized deployment migration step runs `prisma migrate deploy`. Keep migration commands out of request handling/application startup and out of uncontrolled parallel builds. `migrate deploy` alone does not prove drift detection or recovery. Migration smoke fixtures belong to isolated test resources, not invented account/event production schemas.

For failed migration/deployments, stop release, retain sanitized evidence, inspect recorded migration state and choose a reviewed forward repair or tested provider restore. Prefer additive, backward-compatible changes before destructive cleanup. Application-version rollback is valid only while schema compatibility is demonstrated; database rollback and production restore are not automatic or proven by documentation. Actual recovery steps, restore window and data-loss implications require a synthetic exercise against the selected provider.

No user-supplied provider base URL, model override or arbitrary prompt forwarding is exposed through a public probe. Later role operations still require the canonical server identity/role/ownership checks; this foundation introduces no authentication policy or product role.
